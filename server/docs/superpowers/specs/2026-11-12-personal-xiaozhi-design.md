# Личный Xiaozhi и помощник Studio

Пользователь попросил собственное подключение Xiaozhi в каждом личном кабинете,
настройку характера, контекста и разрешённых действий через Studio.

## Границы

Один общий TLS listener маршрутизирует только по проверенному токену устройства.
Каждый обычный кабинет хранит собственную зашифрованную регистрацию Xiaozhi;
пароль официального аккаунта не собирается. Код из личного кабинета пользователь
добавляет в свой агент на xiaozhi.me, затем явно проверяет привязку. Владелец и
существующий пилот сохраняют свои данные и прежний путь. Выбор личного подключения
никогда не подменяется пилотом или платным OpenAI при ошибке.

Для этого запроса прежнее ограничение «голос обычным кабинетам недоступен» меняется
только для их собственных подключений. Общий пилот по-прежнему требует разрешения.
Настройка и отключение не должны затрагивать чужие соединения. Один разговор на
облачную регистрацию, до четырёх разговоров одновременно на один сервер.

Профиль помощника привязан к собственной Киби: character ≤4000 символов, context
≤6000, список идентификаторов разрешённых встроенных действий. Хранится отдельно
в зашифрованном поле кабинета. Произвольных URL, скриптов, импортов или выполнения
загруженного кода нет. Первая поставка действий: прочитать контекст помощника,
прочитать сохранённое состояние собственной Киби, поставить уведомление в её
существующую очередь сообщений. Очередь не доказывает отображение на экране.
Громкость/яркость/эмоции и таймер не объявляются работающими без поддержки прошивки.

## Характер и официальный сервис

В официальном WebSocket-протоколе не найден документированный метод изменения
роли агента. Не используем скрытые API консоли и не называем локальное сохранение
профиля применением системной инструкции в Xiaozhi. Предлагаемый вариант: Studio
составляет текст роли для вставки в консоли; MCP возвращает контекст как данные
инструмента, а не как гарантированную системную инструкцию. Пользователь подтвердил
вариант с одним ручным шагом в Xiaozhi.

MCP реализуется на сервере внутри официального адаптера. Только при наличии
доверенного обработчика объявляется features.mcp. initialize/tools/list/tools/call
получают ограниченные схемы. Обработчик замкнут на аутентифицированные кабинет и
устройство. Нет прозрачного выполнения произвольных запросов облака на плате.
Рабочий аудиотракт PCM/Opus, приветствие и подтверждение воспроизведения сохраняются.

## Доступ Studio

Новые подключения получают assistant.read/assistant.write. Старые подключения
сохраняют прежние права; для новых возможностей нужен новый одноразовый код.
Просмотр и сохранение профиля работают через отдельные серверные маршруты и
инструменты Studio; секреты регистрации никогда не попадают в контекст модели.
Программа, руководство и оверлей обновления должны описывать один контракт.

## Проверки

Два кабинета имеют разные идентичности и шифрованные секреты; настройка, профиль,
контекст и вызовы действий не пересекаются. Проверяются чужой deviceId, просроченный
и отозванный Studio токен, Origin/CSRF, перезапуск, отключение во время запроса,
запоздалые записи регистрации и одновременные разговоры. Внешние ответы Xiaozhi
инъецируются: автоматические тесты не создают реальных агентов и не отправляют
реальные уведомления во внешние сервисы. Локальные проверки не доказывают установки
на VPS, прочтения контекста облачной моделью или физического звука на Киби.

## Рассмотренные подходы

Общий агент владельца не даёт личного характера и облачной идентичности. Отдельный
listener на кабинет конфликтует с портом и TLS. Выбран общий ограниченный шлюз с
независимыми регистрациями и явным маршрутом по токену. Собственный LLM сервер дал
бы автоматический system prompt, но меняет выбранный пользователем сервис Xiaozhi.
