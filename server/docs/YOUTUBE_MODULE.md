# Кадры YouTube для Киби

Модуль `youtube-live` возвращает один беззвучный кадр размером 240×296,
RGB565 little-endian, ровно 142080 байт и SHA-256. Это запрос кадра, а не
непрерывный видеопоток или проигрыватель со звуком. Пример не меняет прошивку,
не подключает устройство и не обращается к сети при публикации пакета.
Наличие исходников не подтверждает работу выбранной трансляции.

## Как устроен доступ

Пример находится в `examples/server-plugin/youtube-live.kibiplugin`:
manifestVersion 2, SDK 1.1, `request-handler`, разрешение
`media:youtube-frame`. Настройки содержат только публичные `videoId` и `fit`.
Начальный ID — `4t4AQ15yj1M`; допустимы ровно 11 символов `A–Z`, `a–z`,
`0–9`, `_`, `-`. Ссылки, произвольные адреса и дополнительные поля
отвергаются. `contain` вписывает кадр с чёрными полями, `cover` заполняет экран
с обрезкой по центру.

Сначала сервер аутентифицирует устройство и проверяет владельца, опубликованный
пакет, включённую привязку и её ревизию. Затем отдельный изолированный
JavaScript worker возвращает описание `youtubeFrame`. Только после проверки
разрешения и актуальной аренды запроса сервер обращается к media adapter.
Запрет или отзыв модуля должен отменять запрос и отклонять запоздалый кадр.
Сам media worker не получает исходник модуля, токен устройства, данные кабинета,
настройки Studio, ключи провайдеров или идентификатор владельца.

В интерфейсе приложения нужны состояния «Подключение», «Нет сети», «Ошибка»,
«Повторить» и «Остановлено». Остановка должна прекращать запросы кадров.
Факт получения байтов не подтверждает частоту кадров, задержку и воспроизведение
на физической Киби.

## Отдельная среда media worker

`createYouTubeFrameService` из `src/plugins/youtube.mjs` выключен по умолчанию.
`status().available` становится true после успешного кадра; до проверки
включённая конфигурация имеет статус `unverified`. Отсутствие Docker, image,
rootless daemon или подходящего видео даёт фиксированный код ошибки, без
исходных исключений, URL и stderr. Никаких подставных кадров при ошибке нет.

Если YouTube требует вход или подтверждение «не бот», запрос кадра возвращает
HTTP 424 и `{ok:false,code:"plugin_media_provider_restricted"}`. Это ограничение
провайдера для текущего видео и исходящего адреса сервера. Проверьте публичную
доступность выбранного видео, повторите позже или явно выберите другой публичный
`videoId`. Доступ в обычном браузере не доказывает доступ из worker на VPS.
Модуль не принимает cookies или учётные данные и не обходит проверку YouTube.

Распознаётся только stderr доверенного yt-dlp, целиком ограниченный 8192 байтами
и удерживаемый в памяти до завершения процесса; исходный текст не передаётся
адаптеру, API или в логи. Worker завершает работу с кодом 1, пустым stdout и
единственной фиксированной строкой stderr
`KIBI_MEDIA_ERROR_V1 plugin_media_provider_restricted`. Адаптер принимает только
точное совпадение всей строки с завершающим LF и без stdout. Примесь других
данных, неправильный exit code и превышение лимита дают обычную фиксированную
ошибку. Успешный stdout по-прежнему содержит только 142080 байт кадра.
Broker разрешает этот код только операции `frame`; ошибка пользовательского
JavaScript не может выдать его за ошибку медиапровайдера.

Доверенный broker с отдельным rootless Docker daemon запускает один контейнер
на кадр. Проверяется `docker info` с `name=rootless`; rootful daemon
отвергается. Основному серверу с аккаунтами не нужно выдавать Docker socket.
Адаптер предназначен для доверенного broker либо отдельного процесса без
данных кабинетов; в контейнер socket не монтируется. Не добавляйте socket или
папки пользователей в основной Compose ради проверки этого примера.

Запуск фиксирует `--pull=never`, пользователя 65532, read-only корень,
`cap-drop=ALL`, `no-new-privileges`, 64 процесса, 512 МиБ, один CPU,
ограниченный noexec tmpfs и отключённый Docker log driver. Нет bind mounts,
наследования окружения хоста в контейнер и доступа к другим проектам.
Одновременно допускается не больше четырёх запросов в процессе broker;
лишние сразу получают `plugin_media_busy`, очереди нет. Общий срок ограничен
20 секундами, включая запас на очистку. Отмена/тайм-аут убивает CLI,
вызывает `docker kill` и `docker rm --force` для случайного имени контейнера;
`--rm` остаётся очисткой со стороны daemon. Команды очистки также ограничены
по времени. Недоступный daemon может помешать немедленной очистке; оператор
должен контролировать его и проверять отсутствие оставшихся контейнеров.

Worker использует только доверенный yt-dlp с фиксированным YouTube extractor,
без конфигурации, cookies, плагинов, автоматического обновления и загрузки
remote components. Официальная onedir-поставка содержит EJS; Node из image —
единственный явно выбранный JS runtime. Полученная строка должна содержать
один HTTPS URL на `googlevideo.com` или `youtube.com` либо их поддомене,
без credentials и нестандартного порта. Адреса сегментов и redirect проходят
такую же проверку. DNS разрешается в публичный IPv4, проверенный адрес
закрепляется в TLS-соединении; приватные, loopback, link-local, документационные
и часть специальных диапазонов отклоняются. IPv6 не используется.

Плейлист ограничен 256 КиБ и глубиной три; выбирается последний доступный HLS
сегмент с необходимым init fragment. Зашифрованные и byte-range плейлисты
отвергаются. Media input ограничен 16 МиБ; большие или неподдерживаемые видео
могут завершиться ошибкой. FFmpeg получает только проверенные байты через
`pipe:0`; его build не содержит сети, а разрешённый protocol — только `pipe`.
Выход — один `rgb565le` кадр через `pipe:1`, без аудио и файлов.

`--network=bridge` разрешает исходящий интернет и **не является egress
песочницей**. Проверки CDN/DNS защищают загрузчик байтов приложения, но
не превращают yt-dlp, его Node runtime или ядро контейнера в сетевой firewall.
Для эксплуатации выделите broker в отдельную сеть/VM без маршрутов к локальным
сервисам и metadata endpoints; задайте egress-политику на уровне firewall или
проверяющего прокси. Она должна разрешать необходимые публичные YouTube/CDN
соединения и DNS. Простого списка доменов в Docker bridge здесь нет.

## Сборка на выделенном Linux broker

Mac пользователя не требует Docker, Python, ffmpeg, yt-dlp или новых пакетов.
Сборка выполняется отдельно из публичного каталога `server/`:

```sh
docker build --file workers/media/Dockerfile --tag kibi-youtube-media:local .
docker image inspect --format '{{.Id}}' kibi-youtube-media:local
```

Сохраните полученный image ID и задайте его доверенной конфигурацией broker;
в production используйте digest/ID проверенного собранного образа. Адаптер
не скачивает image при запросе. Его исходный тег — только локальное имя сборки.
Основной API не должен исполнять загруженный JavaScript в своём процессе и
не должен пересылать непроверенный URL напрямую в media adapter.

В `workers/media/dependencies.json` закреплены Node 24 base image по digest,
build dependencies по согласованным Debian snapshots `bookworm`,
`bookworm-updates` и `bookworm-security` с timestamp `20261116T000000Z`,
FFmpeg 9.0.2 по immutable commit и официальные yt-dlp 2026.10.26 onedir assets
для amd64/arm64 по SHA-256. Security snapshot сохраняет согласованность пакетов
с закреплённым Node base image; apt проверяет подписи Release и суммы пакетов.
Архитектура берётся из непустого `TARGETARCH`; legacy Docker builder при пустом
ARG использует `dpkg --print-architecture` внутри build image. Сборка отклоняет
другую архитектуру и неверную сумму. Никакие инструменты не
скачиваются и не обновляются в момент запроса кадра. При распространении image
сохраните bundled third-party licenses, LGPL notice, исходники FFmpeg либо
доступ к точному исходнику и выполните применимые условия лицензий.

Исходные официальные документы:
[Debian snapshot и его APT-источники](https://snapshot.debian.org/#usage),
[релиз yt-dlp](https://github.com/yt-dlp/yt-dlp/releases/tag/2026.10.26),
[SHA-256 опубликованных assets](https://github.com/yt-dlp/yt-dlp/releases/expanded_assets/2026.10.26),
[параметры и EJS/runtime yt-dlp](https://github.com/yt-dlp/yt-dlp#dependencies),
[исходник FFmpeg 9.0.2](https://github.com/FFmpeg/FFmpeg/commit/946fcce07b6dcd0331c8cc609192aeff5e1924f8),
[protocol whitelist FFmpeg](https://www.ffmpeg.org/ffmpeg-protocols.html),
[scale, pad и crop](https://www.ffmpeg.org/ffmpeg-filters.html).

## Что проверено здесь

Node-тесты используют подставной subprocess/HTTPS transport для проверки
параметров запуска, размеров, валидации адресов, DNS, HLS, переполнения,
тайм-аута и отмены. Проверки ограничений провайдера включают разрыв текста между
stderr chunks, строгий фиксированный маркер, изоляцию кодов runtime/media и
передачу через настоящий локальный IPC/HTTP без обращения к YouTube.
Отдельная проверка запускает собственный Node worker с открытым stdin и
отменяет его, без media tools и сети. Синтетический RGB565 буфер в тесте проверяет
протокол; он не является реальным кадром YouTube.

Две явные проверки настоящего media image в изолированном rootless контейнере
на Linux VPS для `4t4AQ15yj1M` завершились в yt-dlp требованием входа для
подтверждения «не бот». Загрузка media URL и FFmpeg не запускались; ни одного
реального кадра этим запуском не подтверждено. Cookies, авторизация и обходы
ограничений не использовались. Плата не подключалась и не прошивалась.
