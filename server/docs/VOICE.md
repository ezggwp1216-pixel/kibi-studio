# Голос Киби

Для кабинета, подключённого к Studio, действует отдельный
[порядок привязки](STUDIO_CONNECTION.md) и раздел «Shared Xiaozhi pilot
permission» в [API](API.md). Регистрация сама не даёт доступ к личному Xiaozhi
владельца. Владелец явно допускает один кабинет, после чего Studio может выбрать
только его привязанное устройство. Обычному пользователю не выдаются настройки
провайдера, регистрационные коды владельца и ключи. Отзыв допуска отменяет
управляемый голосовой доступ. Лимит первой версии — один активный разговор.

Один процесс обслуживает панель, её зашифрованное хранилище и голосовой TLS-шлюз. Голос выключен по умолчанию. Включение шлюза не отправляет запрос OpenAI: соединение с провайдером возникает после авторизации устройства и правильного `hello`.

В режиме OpenAI шлюз работает с фиксированной моделью `gpt-realtime` и голосом `marin`. Текстовая модель и переключатель текстового ИИ не меняют голос. Сохранённый в панели API-ключ OpenAI используется сервером; ключ не передаётся прошивке. «Характер и инструкции» из панели применяется и к голосу собственных устройств; пустое поле сохраняет короткую русскую инструкцию по умолчанию. Изменение инструкции завершает старый разговор, следующая сессия получит новый характер. В пилотной версии допускается один голосовой разговор одновременно.

## Xiaozhi через собственный сервер

В панели «Модули → Голосовой ИИ» можно явно выбрать Xiaozhi вместо OpenAI. Киби подключается к прежнему адресу нашего сервера; сервер выступает отдельным программным клиентом официального Xiaozhi. Прошивка и экран Киби сохраняются. Это личный пилот: один аккаунт, один явно выбранный проект Studio либо устройство панели, один одновременный разговор. Доступ другим проектам закрыт.

1. Выберите Xiaozhi и идентификатор своего проекта Studio (или устройства панели), сохраните режим.
2. Нажмите «Получить код». Сервер создаст собственную постоянную программную идентичность и запросит привязку. Запросов при открытии страницы нет.
3. Войдите на [xiaozhi.me](https://xiaozhi.me/console/agents), добавьте устройство по шестизначному коду. Код ограничен по времени.
4. Вернитесь в панель и нажмите «Проверить привязку». Модель, язык, инструкции и голос выбираются в официальной консоли Xiaozhi. Сервер не объявляет конкретную модель, которую облако не сообщило.
5. Проверьте два последовательных ответа, длинный ответ и остановку на физической Киби.

Сохранённый режим Xiaozhi никогда автоматически не переключается на платный OpenAI. Опциональный `KIBI_VOICE_PROVIDER=xiaozhi` фиксирует этот режим настройкой запуска; панель не может его изменить. OpenAI для текстовых запросов остаётся отдельным модулем и запускается только явным запросом.

Токен Xiaozhi, программный HMAC и ответ активации остаются в зашифрованном хранилище сервера. Панель получает только состояние и временный код привязки. При изменении режима/проекта/регистрации старый разговор отменяется. Фабричные ключи, MAC чужого устройства и обход аттестации не используются. MQTT-only конфигурация пока не поддерживается; произвольные адреса провайдера не принимаются.

Шлюз нормализует официальный Opus 16/24 кГц в профиль Киби 16 кГц / mono / 60 мс. Локальные идентификаторы, длительность и подтверждение воспроизведения сохраняются. ACK подтверждает воспроизведение на Киби; у облака Xiaozhi нет эквивалента OpenAI history truncate. Прерывание закрывает старый upstream и создаёт новый перед возобновлением, чтобы опоздавший звук не попал в другой ответ. Длительность — число декодированных отсчётов, без обещания определить неизвестное исходное заполнение облачного Opus.

### Завершение отклонённого воспроизведения Xiaozhi

Официальный адаптер Xiaozhi сообщает в ответном `hello` возможности `features:{playback_ack:true,flush:true,playback_resolution:true}`. Приложение может использовать новое событие только при `features.playback_resolution === true`. Адаптер OpenAI эту возможность не объявляет и новое событие не принимает; поведение старого приложения и его аппаратного подтверждения нужно проверять отдельно.

После получения обычного `tts/stop` и завершения очистки своего декодера, программной очереди и DMA приложение может завершить обработку ответа с отказом: например, если mute, текстовый режим или изменение громкости сделали доказательство полного воспроизведения недействительным. Для этого оно отправляет отдельное событие с идентификаторами именно этого ответа:

```json
{"type":"playback_resolution","state":"rejected","response_id":"…","playback_id":"…"}
```

Необязательное поле `session_id` должно совпадать с серверным `hello`. Другие поля, в том числе `audio_end_ms`, запрещены. Это событие означает только завершённую обработку воспроизведения с отказом и готовность продолжить разговор. Оно не подтверждает, что звук был услышан, не меняет фактический частичный `playback` ACK и не вызывает усечение истории облака. При смене громкости или mute приложение должно отменить ожидающее полное подтверждение, если аппаратное доказательство стало недействительным; выдумывать полный ACK нельзя. Само изменение громкости или промежуточный сбой очистки ещё не разрешают отправку события.

Первое событие принимается только для текущего непрерванного завершённого ответа, когда отправка обычного STOP уже началась. Если устройство успело получить STOP раньше завершения серверного обратного вызова записи, сервер сохраняет отказ и ждёт успешного завершения этой записи. Слушание возобновляется только после завершения ответа и записи STOP, затем — полного ACK либо такого явного отказа. Беззвучный ответ без TTS автоматически возобновляет слушание. Пакеты микрофона в полёте и повторный `listen/start` после STOP не заменяют ни ACK, ни отказ.

Повтор уже принятого события с теми же идентификаторами безопасно игнорируется в пределах последних 32 ответов и не открывает микрофон для другого ответа. Событие для прерванного ответа, впервые присланное для старого ответа, с неверными идентификаторами или до отправки STOP завершает сессию с `device_protocol_invalid`. Существующий `abort` сохраняет прежний смысл: прерывает ответ, выдаёт соответствующий flush при отправленном START и закрывает старое соединение с облаком.

Серверные тесты проверяют этот контракт с настоящим локальным Opus и подставным транспортом. Поддержка события самим приложением, изменение громкости во время ответа и два последовательных физических разговора требуют отдельной проверки на Киби; наличие возможности в `hello` этого не доказывает.

В текущем соглашении официального облака бесплатный Open Source режим разрешён для обучения; коммерческие, production- и прибыльные сценарии запрещены. Этот адаптер к официальному облаку предназначен для личного учебного теста. Для пользовательского продукта нужен самостоятельный голосовой сервер с подходящими лицензиями и провайдерами либо коммерческое разрешение сервиса. Принятие соглашения остаётся за владельцем аккаунта.

Консоль может предоставлять Xiaozhi Lite сразу, а Qwen — только после дополнительной проверки GitHub. Не подключайте GitHub автоматически и не называйте фактическую модель Qwen до её выбора и подтверждения в консоли. Бесплатный персональный доступ к Qwen описан в [официальном README Xiaozhi](https://github.com/78/xiaozhi-esp32). Он зависит от правил внешнего сервиса; бессрочный бесплатный или массовый коммерческий доступ не обещается. Протокол основан на [официальном WebSocket контракте](https://github.com/78/xiaozhi-esp32/blob/main/docs/websocket.md) и программной активации [PC-клиента, указанного авторами](https://github.com/huangjunsen0406/py-xiaozhi).

## Настройка запуска

| Переменная | Значение |
| --- | --- |
| `KIBI_VOICE_ENABLED` | Только `1` включает голос; по умолчанию выключен |
| `KIBI_VOICE_HOST` | `127.0.0.1` по умолчанию; в контейнере можно `0.0.0.0`, публикуя порт только на loopback хоста |
| `KIBI_VOICE_PORT` | `9444` по умолчанию |
| `KIBI_VOICE_TLS_KEY_FILE` | Абсолютный путь к приватному PEM-ключу |
| `KIBI_VOICE_TLS_CERT_FILE` | Абсолютный путь к соответствующему действующему PEM-сертификату |
| `KIBI_VOICE_LEGACY_DATA_DIR` | Необязательный абсолютный путь к существующему реестру совместимости Studio; только доверенная настройка процесса |
| `KIBI_COOKIE_PATH` | `/` по умолчанию; `/server/` для панели под этим префиксом |

Ключ и сертификат должны быть обычными файлами без символьных и жёстких ссылок, с правами `600`, `640` или `440`. Владелец — root или пользователь процесса; для root-файлов с групповым чтением процесс должен состоять в их группе. Непосредственный каталог должен быть приватным (`700`/`750`, также допускаются их варианты без записи и с setgid). Небезопасные права, неподходящий ключ, просроченный или ещё не действующий сертификат блокируют голос. HTTP-панель остаётся доступна и показывает причину. Открытого незашифрованного голосового порта нет.

Снаружи устройство подключается к `wss://ваш-домен/kibi-xiaozhi/v1`. HTTPS-прокси должен передавать WebSocket Upgrade в TLS-шлюз, проверяя его сертификат. При публикации панели под `/server/` прокси убирает этот префикс перед передачей в HTTP-панель; ассеты и API панели используют относительные адреса. Голосовой маршрут остаётся в корне домена. На устройстве обязательна проверка сертификата; `setInsecure` не применяется.

## Устройство

1. Сохраните свой API-ключ OpenAI в панели. Сохранение не проверяет баланс или доступ к модели и не отправляет платный запрос.
2. Создайте устройство. Сохраните показанный один раз токен длиной 43 символа.
3. Передайте совместимому приложению Киби адрес шлюза и `Authorization: Bearer <токен>`. Не помещайте токен в URL. Браузерные `Origin` и подпротоколы WebSocket шлюз не принимает.
4. Отправьте `hello`: `{"type":"hello","version":1,"transport":"websocket","audio_params":{"format":"opus","sample_rate":16000,"channels":1,"frame_duration":60}}`.
5. После ответа `hello` отправьте `{"type":"listen","state":"start","mode":"realtime"}` и бинарные Opus-пакеты: mono 16 кГц, кадр 60 мс, не более 1275 байт. Это поток аудио, а не загрузка файла.

Сервер преобразует Opus в PCM 24 кГц для OpenAI и обратно в Opus 16 кГц. Текстовые `stt`/`text` относятся к самому разговору; диагностические статусы не содержат речь, аудио, ключи или токены. `listen/stop` завершает соединение; `abort` прерывает текущий ответ.

Провайдер может сформировать звук быстрее, чем он воспроизводится. Сервер сохраняет темп отправки аудиокадров 60 мс и допускает до 1500 ожидающих сообщений суммарно: аудио, текст и управление. Этот конечный бюджет получен из прежнего срока формирования ответа 90 секунд / 60 мс; он не гарантирует приём 90 секунд аудио. Одновременно действует предел 512000 байт закодированной очереди, прежний срок ответа и ограничения медленного транспорта. После заполнения любого предела сессия закрывается с фиксированной ошибкой; очередь не растёт бесконечно. Прерывание очищает ожидающий ответ, отзыв токена завершает сессию.

Ответ сопровождается `tts/start`, бинарными пакетами и `tts/stop`. Обычный `tts/stop` содержит `response_id`, `playback_id`, `total_samples`, `sample_rate:16000`, `audio_end_ms`; длительность учитывает реальные отсчёты, без дополнения последнего Opus-кадра. Подтверждение `playback` с этими идентификаторами и фактически проигранным `audio_end_ms` следует отправлять после воспроизведения динамиком. Запись в сеть не подтверждает воспроизведение. При `tts/stop` с `flush:true` устройство должно очистить очередь декодера и DMA. При отсутствии аппаратного подтверждения сервер консервативно считает услышанную длительность нулевой для прерывания истории.

Отзыв токена в панели сразу отменяет его разговор. Замена или удаление сохранённого ключа также отменяет разговоры собственных устройств по этому ключу. Авторизация обновляет время последнего запроса устройства. Для проверки качества микрофона, динамика, Wi-Fi, обратной связи и AEC нужна отдельная проверка на физической Киби.

Шлюз не реализует аппаратное эхоподавление и не обещает возможность перебивать Киби голосом во время её ответа. Поведение микрофона при воспроизведении задаёт приложение устройства. Для первого подключения подходит разговор по очереди: приложение временно прекращает отправку микрофона, ждёт фактического завершения воспроизведения и подтверждает его, затем автоматически продолжает слушать. Проверка серверных прерываний в тестах не подтверждает работу такого режима на плате.

## Состояния в панели

- `disabled` — голос выключен настройкой запуска.
- `not_configured` — TLS-шлюз запущен, но нет серверного ключа или доступного реестра совместимости.
- `listening` — TLS-шлюз слушает порт и ожидает устройство; доступ к OpenAI и физический звук не подтверждены.
- `connecting` — устройство подключено, начальная авторизация/подготовка разговора ещё идёт.
- `active` — шлюз получил готовность голосовой сессии. Это не доказательство слышимого звука на плате.
- `error` — шлюз не запущен; `code` содержит фиксированную причину: `tls_required`, `tls_failed`, `legacy_unavailable` или `gateway_unavailable`.

`GET /api/settings` возвращает только безопасный профиль `voice`: `configured`, `enabled`, `status`, `code`, `model`, `endpoint`, `tls`, `legacyConfigured`, `legacyReady`, `activeSessions`. Пути, ключи, токены, аудио и расшифровки туда не попадают. В `/api/overview.modules` тот же профиль находится у модуля `voice`.

## Диагностика своего устройства

В обычном кабинете «Диагностика Киби» показывает только наблюдения сервера об
устройстве этого пользователя. Чтение выполняется через
`GET /api/devices/:id/voice-diagnostics`; подключённый локальный Studio получает
тот же результат через `GET /api/studio/devices/:id/voice-diagnostics` с уже
существующим разрешением `voice.status`. Обновление не подключается к провайдеру,
не отправляет Telegram и не даёт разрешение на голос.

Ответ содержит только `schemaVersion:"1.0"`, `source:"server"`,
`retentionSeconds:3600`, `observed`, `updatedAt`, `connection`, `metrics`, `events`.
До первого сохранённого наблюдения `observed:false`, время, соединение и метрики
равны null, список событий пуст. Это отсутствие наблюдений, а не доказательство
исправности или неисправности устройства. Для наблюдения `connection` содержит
фиксированное состояние `connecting`, `ready`, `closed` или `error`, безопасный
код и признак `active`. Список из максимум 32 переходов содержит только время,
состояние и код. Метрики — null или измеренные целочисленные счётчики пакетов,
байтов PCM, потерь входа, завершённых ответов и отказов воспроизведения. Неизвестные
счётчики отсутствуют; нули не подставляются. Точная схема, имена счётчиков,
пределы и допустимые коды приведены в [API](API.md#private-device-voice-diagnostics).

Данные живут только в памяти один час; общий предел — 512 записей устройств с
вытеснением самых старых. Перезапуск очищает диагностику. Текущие счётчики
обновляются не чаще раза в секунду, переходы состояния и закрытие — сразу.
Речь, аудио, тексты исключений, сырые ответы провайдера, идентификаторы сессий и
ответов, ключи, токены и настройки в неё не попадают. Диагностика не записывается
в файлы, консоль или ленту событий и уведомлений.

Чужое, неизвестное или удалённое устройство возвращает 404 `device_not_found`.
Отозванная или истёкшая авторизация не открывает старые данные. Панель владельца
получает 403 `user_diagnostics_only` при запросе этой диагностики. Когда выбран
делегированный пользовательский пилот, административные профили показывают
только состояние службы: `activityVisibility:"service_only"`,
`activeSessions:null`, `scope:null`, `delegation:null`, `studioAccountId:null`,
а наличие допуска Studio — только булевым `studioVoiceApproved`. Владелец не видит
активность пользователя, его счётчики и коды ошибок сессии через кабинет.
Это разграничение кабинетов; оператор с root-доступом к VPS технически имеет
доступ к самому серверному процессу.

Наблюдения начинаются после успешной авторизации устройства. Они не объясняют
ошибку клиента до авторизации, качество микрофона или физическое воспроизведение
динамиком. Счётчик выходных пакетов и состояние `ready` не доказывают слышимый
звук. Загрузки телеметрии из прошивки и доступа к USB эта версия не добавляет.

## Совместимость с уже выпущенными клиентами Studio

При явном `KIBI_VOICE_LEGACY_DATA_DIR` сервер дополнительно читает существующие `voice.sqlite3` и `master.key` в формате публичного `backend.voice_registry`. Это отдельный read-only реестр возможностей, а не настройки или проекты Studio. Монтируйте каталог только для чтения; ключ и база должны иметь приватные права. Реестр в WAL-режиме не поддерживается. Он не создаётся и не меняется этим сервером.

Токены legacy-клиентов — 64 строчных hex-символа. Допускается только действующее активное поколение, точный официальный endpoint и `gpt-realtime`. Отзыв, истечение срока, смена исходников или конфигурации отменяют активную сессию по проверке метаданных примерно раз в две секунды. Ключ из legacy-реестра не появляется в панели, не переносится в её хранилище и не удаляется вместе с ключом панели. HTTP не может задавать путь к реестру.

Два вида подключений настраиваются независимо. Токен, API-ключ и характер собственного устройства управляются панелью Kibi Server. Поколение токена и ключ legacy-устройства управляются его прежним реестром; характер из панели на него не переносится. Смена или удаление ключа панели не изменяет legacy-реестр, а отзыв legacy-поколения не удаляет собственные устройства панели. Оба вида используют общий шлюз с пределом в один активный разговор. Для самостоятельной установки без существующих клиентов Studio оставьте `KIBI_VOICE_LEGACY_DATA_DIR` незаданным.

## Проверки комплекта

`node --test` проверяет шифрованное хранение, собственные токены, отзыв, реальный локальный TLS/WebSocket с новым временным тестовым сертификатом, закрытие порта, read-only SQLite/AES-GCM совместимость, Opus/ресемплинг, прерывания и ограничения очередей. Тесты не обращаются к OpenAI и не используют ваши ключи. Для TLS-тестов нужна системная команда `/usr/bin/openssl` в macOS/Linux. Она создаёт одноразовую пару ключа и сертификата только во временном каталоге ОС; каталог удаляется сразу после чтения пары. В исходниках и комплекте нет PEM-ключей или готовых тестовых сертификатов. Производственный TLS-сертификат создаётся отдельно и не включается в исходники. Голосовой код использует закреплённые версии `opusscript 0.1.1`/libopus 1.4 и `ws 8.22.1`; лицензии и контрольные суммы находятся в `resources/xiaozhi/`.
