# Выпуск серверных модулей и откат

До рабочего включения на каждой установке отдельно проверить Docker images,
изолированный rootless daemon, доступность выбранного видеоисточника и затем
физическую Киби.
Node/HTTP-тесты не заменяют эти проверки. На Mac пользователя новые пакеты и
постоянно включённый компьютер не требуются.

## Разделение служб

Основной сервер хранит кабинеты и использует только приватный Unix socket
`KIBI_PLUGIN_BROKER_SOCKET`. Он не импортирует Docker executor, не запускает
Docker и не получает его socket. Без брокера модули честно недоступны.

Брокер запускается отдельно через `node src/plugins/broker-main.mjs`.
Только он получает доступ к **выделенному rootless Docker daemon** и
`KIBI_PLUGIN_RUNTIME_ENABLED=1`, `KIBI_PLUGIN_MEDIA_ENABLED=1`. У брокера нет
тома `.data`, пароля администратора, ключей провайдеров или профилей Studio.
Рабочие контейнеры не получают ни Docker socket, ни Unix socket брокера.

Шаблон `compose.plugins.yaml` добавляется к существующему `compose.yaml`.
Брокер и основной контейнер имеют одинаковые настроенные UID/GID; общий том
содержит только Unix socket с правами 0600. Для основного сервера том read-only.
Rootless Docker socket монтируется **только** в контейнер брокера. Docker daemon,
который запускает сам сайт/брокер, не должен совпадать с доступным worker daemon.

## Подготовка оператора

1. Сохранить полный каталог данных текущего сервера и текущие конфигурацию,
   image IDs, исходники и ссылку активного релиза. Данные и ключи хранятся вместе.
   Не выводить их в чат, не включать в пакет и не восстанавливать только state.json.
2. На выделенной Linux-среде установить rootless daemon по официальной
   [инструкции Docker](https://docs.docker.com/engine/security/rootless/).
   Проверить `docker --host <socket> info` и наличие `name=rootless`.
   Обеспечить cgroup/resource limits и сетевую политику media worker по YOUTUBE_MODULE.md.
3. В том же worker daemon собрать `workers/javascript/Dockerfile` и
   `workers/media/Dockerfile`. Сохранить реальные image IDs и задать их в
   `KIBI_PLUGIN_RUNTIME_IMAGE`/`KIBI_PLUGIN_MEDIA_IMAGE`. Автозагрузки образов
   при запросе нет. Брокер собирается из `workers/broker/Dockerfile` отдельно.
4. Задать `KIBI_WORKER_DOCKER_SOCKET` путём к выделенному daemon. На отдельной
   копии данных выполнить `docker compose -f compose.yaml -f compose.plugins.yaml config`.
   Основной сервис не должен иметь mount Docker socket; брокер — каталогов данных.
5. Запустить сначала тестовый экземпляр без настоящих пользовательских устройств.
   Проверить /api/health, вход, личного Xiaozhi, сохранение старых подключений,
   создание новой ссылки с разрешением на модули и полный цикл пакета.

Реальные проверки исполнителя: обычный ответ, ошибка handler, следующий
успешный вызов, timeout, отмена, превышение вывода, отсутствие оставшихся
контейнеров, отключение пакета во время работы, недоступный daemon.
Обычная ошибка handler не должна отключать общий runtime. При cleanup_failed
проверить контейнеры и только затем перезапустить брокер и основной процесс,
чтобы очистить карантин. Не сбрасывать его циклическим автоперезапуском.

### Восстановление после аварии брокера

При SIGKILL, OOM или аварийном выключении в IPC-томе может остаться
`/run/kibi-executor/worker.sock`. Брокер намеренно отказывается занимать уже
существующий путь: старый процесс или его задачи могут быть ещё живы.
Автоматический restart брокера в overlay выключен. Сервер кабинетов может
продолжить работу, но модули останутся недоступны до проверки оператора.

1. Остановить приём вызовов и оба сервиса `kibi`/`kibi-plugin-broker`. Проверить,
   что другой экземпляр брокера с этим томом тоже не запущен.
2. В выделенном rootless worker daemon перечислить все оставшиеся задачи.
   Сверить их с префиксами `kibi-plugin-`/`kibi-media-` из этого релиза и
   остановить/удалить только подтверждённые задачи Киби. Убедиться, что они
   исчезли; при недоступном daemon продолжать восстановление нельзя.
3. Проверить отсутствие живого listener на известном IPC-пути, например
   через `ss -xlpn` в среде, где виден этот том. Само наличие файла не
   подтверждает, что брокер остановлен. Пока владелец listener или задачи
   не установлены, socket не удалять и не сбрасывать карантин.
4. После этих проверок от имени настроенного UID в **точном IPC-томе**
   удалить только оставшийся `worker.sock`. Сначала проверить через `lstat`,
   что это Unix socket владельца с ожидаемым UID, а не ссылка/обычный файл.
   Не удалять весь том, Docker socket или каталог данных; не использовать
   шаблоны удаления. Доступ к тому для этой операции получает только оператор.
5. Запустить брокер, затем основной сервис; проверить `/api/health`,
   фактические capabilities и один явный тестовый вызов. Если очистка или
   запуск не доказаны, оставить модули отключёнными и разбираться в причине.

Эта процедура также обязательна перед сбросом `cleanup_failed`: простой
перезапуск процессов не доказывает, что оставшийся контейнер прекратил работу.
После штатной остановки Node удаляет свой socket; ручная очистка обычно не нужна.

Для медиа получить именно кадр указанного эфира, сверить длину и SHA-256,
сохранить измеренные время и задержку. После этого проверить реальные кадры,
остановку, восстановление сети и устойчивость на привязанной Киби. Пока
эти этапы не выполнены, голос и видео не объявляются проверенными на железе.

## Комплекты Studio

Серверный архив и локальная Studio выпускаются отдельно. В этом кандидате
сервер отдаёт проверяемый overlay через `/studio/modules/release.json`,
архив и его `.sha256`; исходники и updater лежат в `studio-integration/`.
Обновлятор применяется только к поддержанной публичной основе после проверки
хешей. Не переносить целиком старую ветку или чужой каталог проектов.

Для новой установки подготовлен полный `studio-full-server-modules-20261117-rc1`.
Он содержит проверенный bootstrap, интеграцию модулей и актуальные публичные
инструкции; нейтральный стартовый проект сохраняется. При публикации нужно
использовать согласованные release/manifest/archive и точный новый Git-коммит,
затем пройти путь новой установки именно по этой ссылке. Внутренний lineage/base
SHA описывает происхождение, а не адрес установки нового комплекта.
Существующий `/studio/release.json` этим кандидатом не подменяется, чтобы не
смешать поставки. Обновление личной Studio и публикация на GitHub здесь
не выполняются автоматически.

## Включение и возврат

После всех проверок остановить новые запросы модулей, дождаться завершения
исполнителей, сделать согласованную резервную копию данных и переключить
код текущего сервера на проверенный новый релиз. Не заменять работающий
сервер старой веткой `4a75f3ed`; комплект содержит сохранённую актуальную
основу личного Xiaozhi и текущих прав Studio.

Откат одного приложения выполняется через ревизии привязки в кабинете.
Откат всего выпуска — другая операция:

1. Отключить приём вызовов модулей, завершить и проверить контейнеры; остановить
   новый сервер и брокер. Убедиться, что старый сервер не работает одновременно.
2. Пока основной сервер остановлен, выполнить описанный ниже офлайн-отзыв новых
   Studio-подключений. Сохранить весь каталог данных, конфигурацию и исходный релиз.
3. Вернуть предыдущие проверенные код/image IDs и конфигурацию; убрать только
   подключение брокера. Запускать старый backend только после успешной проверки
   совместимости `studio-links.json`. Возврат согласованной полной резервной копии
   вместо миграции потеряет изменения кабинетов после её создания и требует
   отдельного решения владельца.
4. Каталог реестра модулей оставить на диске для возврата нового выпуска.
   Старый сервер не должен его исполнять. Не удалять `.data`, ключи, аккаунты,
   привязки устройств и регистрацию Xiaozhi.
5. Проверить вход, свои устройства, голос и исходные настройки. Локальную
   Studio вернуть из сохранённой публичной копии либо оставить с честным
   «сервер не поддерживает модули»; личные проекты не переносить поверх неё.

### Офлайн-отзыв Studio-подключений с правами модулей

Команды выполняются из `server/` новым релизом на Node 24, от имени владельца
файлов данных. `--data-dir` всегда задаётся явно; переменные окружения и рабочий
каталог не выбирают базу. Здесь приведены примеры путей: оператор подставляет
свой каталог, а не переносит рабочие данные в исходники или пакет выпуска.

Сначала выполнить dry-run. Он не создаёт каталогов, файлов, блокировок или копий:

```sh
node scripts/retire-plugin-links.mjs --data-dir /srv/kibi/data
```

Вывод содержит только счётчики и SHA-256 файлов. `sourceSha256` — SHA исходного
`studio-links.json`, `resultSha256` — SHA предполагаемого результата;
`changedFiles` в dry-run равен 0. Счётчики `revokedPluginConnections` и
`revokedPluginPendingCodes` показывают число записей, подлежащих отзыву.
Email, ID, labels, токены и хеши отдельных учётных записей не выводятся.

Если отзывов нет, менять файл не требуется. Если `registryFiles` равен 0,
студийного реестра нет: SHA равны `null`, выполнение успешно завершается без
записей. Приватный каталог данных при этом должен уже существовать.

Для применения остановить сервер и брокер, проверить dry-run и передать его
`sourceSha256`. Путь `--backup` должен обозначать **новый** файл в уже существующем
приватном каталоге резервных копий. Каталоги данных/копии должны принадлежать
текущему пользователю с правами 0700, реестр — с правами 0600. Символические
ссылки в путях, hardlinks файлов и чужой владелец отклоняются; инструмент
не исправляет права автоматически. Каталог копий хранится вне пакета и Docker
build context. Все четыре подтверждения обязательны:

```sh
node scripts/retire-plugin-links.mjs --data-dir /srv/kibi/data \
  --apply --expected-sha256 '<sourceSha256 из dry-run>' \
  --backup /srv/kibi/private-backups/studio-links-before-rollback.json \
  --confirm-server-stopped
```

Инструмент проверяет весь формат v1 до записи. Он отзывает только подключения
с точным новым набором десяти прав и ожидающие коды с `pluginAccess:true`.
Старые подключения с пятью/семью правами и обычные ожидающие коды сохраняются
побайтно внутри JSON; их сроки и права не меняются. Понижения десяти прав до
семи нет: после возврата нового релиза отозванному Studio потребуется новая
явная привязка. Неизвестные поля, порядок/состав прав, дубликаты и некорректные
записи приводят к отказу до создания резервной копии.

Копия создаётся через эксклюзивное открытие (`wx`, 0600) и никогда не
перезаписывается; её байты и SHA проверяются до замены реестра. Результат
пишется в приватный временный файл с `fsync`, затем атомарно заменяет только
`studio-links.json`. Исходный SHA, приватность путей и копия проверяются
повторно перед `rename`; несовпадение останавливает применение. Успешный вывод
содержит `changedFiles:1` и `backupSha256`. При отказе после создания копия
может остаться на диске: сохранить её и разобраться в причине, не заменять
автоматически. Флаг остановки — подтверждение оператора; CLI не устанавливает
блокировку и не останавливает другие процессы за него.

Повтор той же команды на уже очищенном валидном реестре — успешный no-op
с `changedFiles:0`: дополнительная копия не создаётся, существующая не меняется.
Это также действует при устаревшем ожидаемом SHA, поскольку записей уже нет.
При наличии записей для отзыва SHA обязан совпасть с текущим dry-run.
Отсутствующий реестр также остаётся no-op; флаги применения всё равно обязательны.

Если на VPS нет Node 24, офлайн CLI включён и в новый серверный image.
Можно запустить его отдельным контейнером без сети при остановленных службах,
смонтировав **только** каталог данных и приватный каталог копий, с теми же
UID/GID владельца данных. Например, dry-run:

```sh
docker run --rm --pull=never --network=none --read-only \
  --user '<UID>:<GID>' --cap-drop=ALL --security-opt=no-new-privileges:true \
  --mount type=bind,src=/srv/kibi/data,dst=/data \
  --entrypoint node '<проверенный новый image ID>' \
  scripts/retire-plugin-links.mjs --data-dir /data
```

Для применения нужны все прежние флаги и отдельный writable mount приватного
каталога резервных копий. Не подключать Docker socket и не использовать
старый image, в котором этого инструмента нет.

CLI не открывает `accounts.json`, state, ключи шифрования, устройства, Xiaozhi
или реестр модулей. Он не запускает backend, Docker, сеть и пользовательский код.
Проверка на синтетических данных:

```sh
node --test tests/plugin-rollback-format.test.mjs
node --test
```

Автоматическое изменение рабочей базы и откат на VPS этим документом не выполняются.
